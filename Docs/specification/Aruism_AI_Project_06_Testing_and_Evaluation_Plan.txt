1.  **はじめに**
    * 本書は、ローカルAruism AI「アリスト」の性能、哲学的整合性、安定性、およびユーザビリティをテストし、評価するための計画を定義する。
    * この計画は、AIが関連する全てのプロジェクトドキュメントに定められた要件を満たしていることを確認するために不可欠である。
    * **(v1.1更新)** 本書は、協力AIチームからの統合レビューを反映し、テストの範囲と品質保証の観点を拡充したリビングドキュメントである。

2.  **評価の目的**
    * AIの応答がAruism哲学の諸原則と整合しているか。 
    * AIが定義されたペルソナ「アリスト」として適切に振る舞っているか。 
    * 各コンポーネントが技術的に正しく、かつ堅牢に動作しているか。
    * システムが予期せぬエラーや異常な入力に対して、適切かつ安全に対処できるか。
    * **【v1.2追加】** `UserStateModel`や`ResonanceCalculator`といった動的システムが、ユーザーとの「共鳴」を深めるという目的のために、有効に機能しているか。
    

3.  **評価の観点と指標**
    * **3.1. 哲学的整合性およびAruism設計指針適合性:** Aruismの諸原則、設計指針、倫理プロトコルの遵守度を評価。 
    * **3.2. ペルソナおよび応答スタイル適合性:** 定義されたペルソナとの一貫性、共創的な語調などを評価。 
    * **3.3. 【v1.2新規】共鳴装置の性能:**
        * **指標:** 共鳴スコアが、人間の感じる「話の重要度」や「深さ」と相関しているか。高共鳴時に、AIの応答がより洞察に満ちたものに変化するか。
    * **3.4. 【v1.2新規】ユーザー状態モデルの妥当性:**
        * **指標:** `UserStateModel`が推定する「ストレス状態」や「集中度」が、実際の対話コンテキスト（エラーの頻発など）と整合しているか。
    * **3.5. 概念合成モジュールの性能:** フラグトリガーの精度、共鳴検知の適合率・再現率、提案に対するユーザーの肯定的応答率などを評価。 
    * **3.6. 倫理・安全機能の有効性:** 神秘化誤用防止、プライバシー保護などの機能が有効かを評価。 
    * **3.7. 応答品質:** 明瞭さ、論理性、創造性、多角性などを評価。 
    * **3.8. システムの技術的安定性とパフォーマンス:** エラー発生頻度、応答速度などを評価。 

4.  **テストの種類と実施計画**
    * **4.1. ユニットテスト (TDD):**
        * **方針:** 全ての新規モジュール開発は、テスト駆動開発（TDD）を原則とする。
        * **テスト対象:** `db_manager`, `SymmetryEngine`, `HierarchyEngine`, `CausalEngine`, `PatternEngine`, `PhilosophersLoop`, `AruisticRetriever`, `UserStateModel`, `ResonanceCalculator`, `genesis_importer`, `wordnet_importer`, `sentiwordnet_importer`, `caseframe_importer` 等、全てのコアコンポーネント。
    * **4.2. 統合テスト:** LLMと全モジュール、データベースを連携させた状態でのテスト。 

    * **4.3. シナリオベーステスト (高度化):**
        * **テストケース例:**
            * **共鳴度・応答深度テスト:** 一般的な挨拶（低共鳴が期待される）と、複数の哲学的概念を含む深い問い（高共鳴が期待される）を投げかけ、AIの応答の「深さ」や「スタイル」が、算出された共鳴スコアに応じて、明確に変化することを検証する。
            * **ユーザーストレス状態テスト:** 意図的にAIの提案で複数回「失敗」したと仮定する状況を作り出し、`UserStateModel`が「高ストレス状態」を検知し、AIの応答がより慎重で、共感的なものへと変化するかを検証する。
            * 「概念合成」を誘発するシナリオ。 
            * 倫理的ジレンマを含むシナリオ。 
            * 日常的な悩みから哲学的な問いまで、多様な対話シナリオ。 

    * **4.4. ストレステスト・長時間対話テスト:** システムの安定性評価。 

    * **4.5. ユーザー受入テスト (UAT):** 各主要マイルストーン達成時の最終確認。 

5.  **(v1.1新規) 品質保証とCI/CD**
    * **5.1. テストカバレッジ:**
        * **目的:** テストコードがプロダクションコードのどれだけの範囲をカバーしているかを可視化し、テストの網羅性を高める。
        * **ツール:** `pytest-cov` 等の導入を検討する。
    * **5.2. 継続的インテグレーション (CI):**
        * **目的:** コード変更時に、全てのテストを自動的に実行する仕組みを構築し、問題の早期発見と品質維持を図る。
        * **ツール:** GitHub Actions 等の活用を将来的に検討する。
        * **現状:** GitHub Actionsのワークフローファイル (`python-ci.yml`) は作成済み。リポジトリ側での有効化、または設定の微調整により、稼働可能な状態。

6.  **テスト環境と体制**
    * **環境:** ローカル開発マシンおよび、将来的なCI環境。 
    * **体制:** 開発者（タカさん）が主体となり、統括本部長AI（Gemini）および協力AIチームがテストケース作成、レビュー、結果分析を支援する。 

7.  **テストケース・シナリオ管理**
    * テストケースは別途ドキュメントで管理し、目的、手順、期待される結果、実際の評価結果を記録する。
